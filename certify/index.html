Post-Quantum Certificates

Signed acknowledgement certificates, verified in your browser with ML-DSA-87 (NIST FIPS 204).

What these certificates are

When a security report I receive is validated, I may issue a certificate acknowledging it. The certificate is a plain JSON file containing the exact claims (subject, date, what was acknowledged) plus a digital signature over those claims. Nothing is stored on any server beyond the public files themselves.

The signature uses ML-DSA-87, the highest security level of NIST's FIPS 204 post-quantum signature standard. Because browsers do not yet ship post-quantum algorithms in WebCrypto, verification runs through @noble/post-quantum, a small audited pure-JavaScript implementation self-hosted on this site.

How verification works

  1. The certificate carries its certificate ID — the first 16 hex characters of the SHA-256 hash of the signed claims.
  2. The verify page fetches the certificate (via the ID or the embedded link) and the site's single public key.
  3. It checks the hash matches, then checks the ML-DSA-87 signature against the exact signed bytes using the public key.

Only the signer's private key (never on this site) can produce a signature the public key accepts — so a valid certificate is mathematically provable as issued by me, and any tampering is detected immediately.

Verify a certificate

Open the verification page and paste a certificate, or follow the certificate's own link. A printable certificate card is shown for every valid certificate.

What a certificate does and doesn't prove

It proves hardik-pandey.com issued this exact signed statement about this subject on this date. It does not prove the person presenting it is that subject, and it cannot be revoked once issued — the signature remains valid as long as the public key is in use. Treat it as a signed acknowledgement, not an identity document.

Technical details, the key model, and the minting tooling are documented in certify/README.md.
